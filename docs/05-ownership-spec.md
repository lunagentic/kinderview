# 05. 담당 정의 스펙

## 5.1 기본 개념

KinderFlow는 업무를 **배정(assign)** 하지 않는다.
"이 업무를 **누가 담당하고 있는가**"를 명확히 **정의(define)** 한다.

| 배정 시스템 | KinderFlow |
|---|---|
| 관리자가 구성원에게 일을 내린다 | 진행 중인 업무의 책임 주체를 기록한다 |
| 미배정 상태가 존재한다 | 담당자 없는 업무는 존재할 수 없다 |
| 수락/거절 개념 | 없음. 사실을 기록할 뿐 |
| 여러 명에게 배정 | 담당자는 1명. 나머지는 협업자 |

이 차이가 UI 문구에도 반영된다.

| 지양 | 사용 |
|---|---|
| 업무를 배정했습니다 | 담당 업무가 등록되었습니다 |
| 담당자 할당 | 담당자 |
| 미배정 | (존재하지 않음) |

## 5.2 담당은 영역 리드가 맡는다

> 2026-09-04 변경 — 업무마다 담당자를 고르던 방식을 **영역 리드** 방식으로 바꿨다.

업무 등록 화면에는 **담당자 선택 항목이 없다.** 업무 영역을 고르면
그 영역의 리드가 자동으로 담당이 된다.

```
업무 영역   디자인
   ↓
담당       정OO   (디자인 영역 리드)
```

| 역할 | 인원 | 정의 | 알림 |
|---|---|---|---|
| **영역 리드** | 영역당 1명 | 그 영역 업무의 책임 주체. 업무의 담당자가 된다 | 등록, 마감, 지연, 검수, 이슈 |
| **협업자** | 업무당 0~N명 | 함께 참여하거나 확인이 필요한 구성원 | 등록 시 1회 |

### 왜 바꿨나

소규모 팀에서 업무마다 사람을 지정하는 것은 관리 비용만 늘린다.
실제로 "이건 누가 하죠?"의 답은 대부분 **직능**으로 정해져 있다 — 디자인은 디자인 리드가 본다.
영역에 리드를 두면 업무를 넣을 때 사람을 고르는 단계가 사라지고,
기록 마찰이 줄면서도 책임 주체는 여전히 한 명으로 명확하다.

원칙 1(담당을 명확히 정의한다)은 그대로다. **정의하는 단위가 업무에서 영역으로 올라갔을 뿐이다.**

### 규칙

- 한 사람이 여러 영역의 리드를 겸할 수 있다.
- **리드가 없는 영역에는 업무를 만들 수 없다.** 담당 없는 업무를 막는 장치가 그대로 작동한다.
- 업무의 영역을 바꾸면 담당도 새 영역의 리드로 따라간다.
- 리드를 교체하면 그 영역의 **미완료 업무** 담당이 함께 옮겨지고 `TASK_EVENT(OWNER_CHANGED)`가 남는다.
  **완료된 업무는 당시 담당자를 그대로 유지한다** — 지난 일의 책임자는 바뀌지 않는다.
- 협업자는 업무 단위로 그대로 지정한다. 담당(리드)을 협업자로 중복 등록할 수 없다.

### 이슈는 다르다

이슈 담당자는 여전히 **사람을 직접 지정**한다. 이슈는 영역에 매이지 않고,
해결 주체가 그 영역의 리드가 아닐 때가 많다.

## 5.3 Slack 멤버 연동

내부 구성원은 **별도의 구성원 DB를 만들지 않고** Slack Workspace 멤버를 기준으로 한다.

### 연결하는 정보

| KinderFlow | Slack API 필드 |
|---|---|
| Slack User ID | `user.id` |
| 이름 | `user.profile.display_name` (없으면 `real_name`) |
| 프로필 이미지 | `user.profile.image_72` |
| 이메일 | `user.profile.email` (권한 있을 때) |

### 동기화

| 항목 | 정책 |
|---|---|
| 방식 | `users.list` 전체 조회 후 upsert |
| 주기 | 1일 1회 (매일 08:00) + 관리 화면의 `지금 동기화` 수동 실행 |
| 제외 대상 | `is_bot = true`, `deleted = true`, `Slackbot` |
| 퇴사/삭제 | 레코드 삭제하지 않고 `is_active = false` |
| 신규 멤버 | 자동 추가. 별도 초대 절차 없음 |

### 담당자 선택 UI

```
담당자 *
┌────────────────────────────┐
│ 🔍 Slack 멤버 검색          │
├────────────────────────────┤
│ (img) 김OO      @kim        │
│ (img) 박OO      @park       │
│ (img) 이OO      @lee        │
└────────────────────────────┘
```

- 이름·Slack 핸들·이메일로 검색한다.
- 최근 지정한 담당자 3명을 상단에 노출한다.
- 비활성 멤버는 검색 결과에 노출하지 않는다. 단, 기존 업무의 담당자로는 계속 표시하고
  `(비활성)` 배지를 붙인다.

### 비활성 멤버 처리

퇴사·삭제된 멤버가 담당인 업무가 남을 수 있다. 이때:

- 비활성 구성원이 리드로 남은 영역은 **위험 신호**(`HANDOVER`)로 Overview 상단에 노출한다.
- 해당 업무는 프로젝트/영역 집계에서는 정상 포함한다.

## 5.4 외주 작업의 담당 정의

외주는 **내부 담당자**와 **외부 작업자**를 구분한다.

| 구분 | 값의 출처 | 필수 |
|---|---|---|
| 내부 담당자 | Slack 멤버 (`task.owner_slack_user_id`) | ✔ |
| 외주 업체 | 직접 입력 (자동완성) | ✔ |
| 외부 작업자 | 직접 입력 | |

```
업무        활동지 디자인 제작
외주 업체    OO 디자인
외부 작업자  홍길동
내부 담당자  @김OO
납품 예정    9/15
현재 상태    작업중
```

- 외부 업체·작업자는 KinderFlow 계정이 아니다. 알림 대상도 아니다.
- 알림은 모두 **내부 담당자(= 외주 영역 리드) 기준**으로 동작한다.
  외주 업무의 진행 책임은 외부가 아니라 내부 담당자에게 있다. (원칙 5)
