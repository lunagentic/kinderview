# 12. AI 기능 스펙

## 12.1 왜 지금 AI인가

KinderFlow의 가장 큰 리스크는 기능 부족이 아니라 **기록이 습관화되지 않는 것**이다
([10.7 리스크](10-roadmap-backlog.md#107-리스크)). 그리고 기록이 쌓여도
"52건 중 지연 5건"이라는 숫자만으로는 **무엇이 위험한지** 알 수 없다.

AI가 KinderFlow에서 할 일은 두 가지뿐이다.

1. **기록의 마찰을 줄인다** — 한 줄로 쓰면 업무가 된다
2. **숫자에서 판단으로 넘어간다** — 지연 5건이 아니라 "이 3건이 위험하다"

이 둘에 해당하지 않는 AI는 넣지 않는다.

## 12.2 레퍼런스 검토 — monday.com AI 에이전트

monday.com은 AI를 "디지털 인력(digital workforce)"으로 포장해 카드 단위로 판다.

| monday.com | 하는 일 | KinderFlow 적용 |
|---|---|---|
| **Project Monitor** — Surfaces hidden risks | "우리 프로젝트 어때?" → 포트폴리오 상태 요약 | **채택.** 단 "요약"이 아니라 **위험 신호 감지**로 좁힌다. 요약은 이미 Overview가 한다 |
| **Content Creator** — Drafts in your voice | 브랜드 보이스로 초안 작성 | **부분 채택.** 마케팅 카피가 아니라 **Weekly Report 요약문** 작성으로 좁힌다 |
| **Meeting Scheduler** — Syncs impossible calendars | 캘린더 조율, 초대 발송 | **채택하지 않는다.** KinderFlow는 Google Calendar를 대체하지 않는다 ([원칙 §1.7](01-service-overview.md#17-서비스별-역할-분담)) |

### 레퍼런스에서 가져오지 않은 것

- **에이전트 의인화** — 캐릭터·이름·"당신의 팀원" 서사. 기대치만 부풀린다
- **대화형 UI** — 챗봇 입력창. 물어볼 것을 사용자가 매번 생각해야 한다.
  KinderFlow는 **묻지 않아도 먼저 보여준다**
- **"자동으로 처리했습니다"** — 업무 상태를 AI가 바꾸지 않는다. 담당은 사람이 정의한다 (원칙 1)

## 12.3 KinderFlow AI 3종

| # | 이름 | 하는 일 | LLM 필요 |
|---|---|---|---|
| ① | **위험 신호** (Risk Monitor) | 지연·정체·병목·부하를 데이터에서 찾아낸다 | **불필요** — 전부 규칙 |
| ② | **주간 요약문** (Weekly Digest) | Weekly Report 숫자를 공유용 문장으로 만든다 | 선택 — 없으면 템플릿 |
| ③ | **빠른 입력** (Quick Capture) | 한 줄 문장을 업무 필드로 바꾼다 | 선택 — 없으면 규칙 파서 |

### 설계 원칙

1. **AI 없이도 완전히 동작한다.** Slack 연동과 같은 방식이다. 키가 없으면 규칙으로 돌고,
   키가 있으면 같은 자리에서 더 잘 돈다.
2. **AI는 쓰지 않고 보여준다.** 상태 변경·담당자 지정·삭제를 AI가 실행하지 않는다.
   ①은 읽기 전용, ②는 문장 생성, ③은 **폼을 채워줄 뿐 저장은 사람이 누른다.**
3. **근거를 함께 보여준다.** 모든 위험 신호는 어떤 업무·어떤 이력에서 나왔는지 링크로 연결된다.
   "AI가 그렇다더라"로 끝나는 항목을 만들지 않는다.
4. **틀려도 안전한 자리에만 쓴다.** LLM이 틀리면 문장이 어색하거나 폼이 잘못 채워질 뿐이다.
   집계·진행률·지연 판정에는 LLM을 쓰지 않는다.

## 12.4 ① 위험 신호 (Risk Monitor)

Overview 최상단에 노출한다. 규칙 기반이므로 결과가 항상 같고 설명 가능하다.

| 코드 | 위험 | 판정 | 중요도 |
|---|---|---|---|
| `REPEATED_POSTPONE` | 마감이 반복해서 밀린다 | `DUE_CHANGED` 이력 2회 이상 & 미완료 | 높음 |
| `STALLED` | 진행중인데 멈춰 있다 | 진행 단계 & 마지막 상태 변경 후 7일 경과 | 보통 |
| `REVIEW_BOTTLENECK` | 검토에서 막혀 있다 | 검토·검수 단계 & 5일 경과 | 보통 |
| `DELIVERY_AT_RISK` | 납품일이 다가오는데 진척이 없다 | 외주 & 납품 D-3 이내 & 아직 `요청 완료` 이하 | 높음 |
| `REJECTED_IDLE` | 반려된 외주가 방치돼 있다 | 검수 `반려` & 상태가 `수정`이 아님 | 높음 |
| `OWNER_OVERLOAD` | 한 사람에게 마감이 몰린다 | 같은 담당자의 7일 내 마감 4건 이상 | 보통 |
| `ISSUE_OVERDUE` | 이슈 해결 목표일이 지났다 | 미해결 & 목표일 < 오늘 | 높음 |
| `ISSUE_STALE` | 중요 이슈가 오래 열려 있다 | 중요도 높음 & `OPEN` 7일 경과 | 보통 |
| `HANDOVER` | 비활성 담당자의 업무가 남아 있다 | 담당자 비활성 & 미완료 | 높음 |
| `PROJECT_SLIPPING` | 프로젝트 지연 비중이 높다 | 미완료 중 지연 30% 이상 & 2건 이상 | 보통 |

- 정렬: 중요도 내림차순 → 관련 건수 내림차순
- 각 항목은 **근거가 되는 업무/이슈로 바로 이동**한다
- 위험이 없으면 "지금 눈에 띄는 위험 신호가 없습니다"를 보여준다 (빈 상태도 정보다)

**의도적으로 넣지 않은 규칙**
- "완료율이 낮다" — 프로젝트 초반에는 당연히 낮다. 노이즈만 만든다
- "설명이 비어 있다" — 기록 부담을 늘리는 방향은 원칙에 어긋난다

## 12.5 ② 주간 요약문 (Weekly Digest)

Weekly Report의 9개 섹션은 숫자와 목록이다. 팀·경영진에 공유할 때 필요한 건 문장이다.

- 입력: 해당 주 스냅샷 + 위험 신호
- 출력: **요약 3~4문장 + 주목할 점 3개 + 다음 주 초점 1~2개**
- LLM 없을 때: 같은 데이터로 템플릿 문장을 만든다 (숫자는 동일, 문장이 덜 자연스러울 뿐)
- 생성된 문장은 **리포트에 저장되지 않는다.** 매번 현재 데이터로 다시 만든다

**LLM에 넘기지 않는 것**: 원본 업무 설명 전문, 개인 이메일. 집계 수치와 업무명까지만 보낸다.

## 12.6 ③ 빠른 입력 (Quick Capture)

업무 등록 모달 최상단에 한 줄 입력을 둔다.

```
9/15까지 김OO 활동지 디자인 외주 검수, 콘텐츠 패키지
   ↓
업무명   활동지 디자인 외주 검수
프로젝트  콘텐츠 패키지
영역     외주 작업
담당자    김OO
마감일    2026-09-15
```

- 인식 대상: 날짜(오늘/내일/이번주 금요일/다음주/9월 15일/9/15/3일 뒤), 담당자(구성원 이름·핸들),
  프로젝트(이름·약칭), 업무 영역(키워드), 우선순위(긴급·중요)
- **채워주기만 한다.** 저장 버튼은 사람이 누른다. 잘못 채워졌으면 그냥 고치면 된다
- 인식 실패한 필드는 비워 둔다. 억지로 추측하지 않는다

## 12.7 기술 구조

```
server/ai/
  rules.js      규칙 엔진 — 위험 감지 · 요약 초안 · 문장 파싱 (LLM 불필요, 순수 함수)
  provider.js   Anthropic SDK 어댑터 (선택적 의존성)
  index.js      규칙 → LLM 순서로 처리하고 실패하면 규칙 결과를 그대로 반환
```

| 항목 | 값 |
|---|---|
| 모델 | `claude-opus-5` |
| SDK | `@anthropic-ai/sdk` (**optionalDependencies** — 설치되지 않아도 앱이 동작한다) |
| 활성 조건 | `ANTHROPIC_API_KEY` 환경변수가 있을 때만 |
| 구조화 출력 | `strict: true` 도구 + `tool_choice` 강제 — 스키마에 맞는 JSON만 받는다 |
| 실패 처리 | 모든 LLM 호출은 try/catch. 실패하면 규칙 결과를 그대로 쓴다. 사용자에게 오류를 던지지 않는다 |
| 타임아웃 | 15초. 초과 시 규칙 결과 |

### API

| 메서드 | 경로 | 설명 |
|---|---|---|
| GET | `/api/ai/risks` | 위험 신호 목록 (규칙, 항상 동작) |
| POST | `/api/ai/digest` | 주간 요약문 생성 (`{ week }`) |
| POST | `/api/ai/capture` | 한 줄 문장 → 업무 필드 (`{ text }`) |

응답에는 항상 `source: "rules" | "llm"` 을 실어 **무엇이 만든 결과인지 화면에 표시**한다.

## 12.8 비용과 한계

- ①은 LLM을 쓰지 않으므로 **비용 0**이다. AI 기능 중 가장 값어치가 큰 것이 공짜인 구조다
- ②는 주 1회, ③은 업무 등록 시에만 호출한다. 호출량이 작다
- **한계**: ③의 규칙 파서는 한국어 문장 형태에 따라 실패한다. 실패하면 빈 폼일 뿐이므로
  손해가 없다. LLM을 붙이면 이 실패율이 크게 줄어든다

## 12.9 범위에서 뺀 것

| 안 넣은 것 | 이유 |
|---|---|
| 업무 자동 생성·자동 배정 | 원칙 1 위반. 담당은 사람이 정의한다 |
| 회의 일정 조율 | Google Calendar 영역 |
| 챗봇 인터페이스 | 물어볼 것을 사용자가 생각해야 한다. 먼저 보여주는 쪽이 낫다 |
| 업무 우선순위 자동 산정 | 근거를 설명할 수 없으면 신뢰받지 못한다 |
| 지연 예측(ML) | 데이터가 쌓이기 전엔 추측이다. 규칙으로 충분히 잡힌다 |
